## 1. 目标

给每种控制端一块合身的屏：

- 手机竖着用：竖屏（即现在的手机屏）
- 手机横着用：横屏
- 平板：横屏；竖着用时选竖屏
- 电脑：横屏
- 换着用不同设备远程同一台 Mac：各有各的屏，换设备（包括在另一台上点「接管设备」）不用改任何设置

UU远程 同一时刻只让一台设备控制一台 Mac：第二台连上来只能「接管设备」，把前一台挤下去（实测见第 7 节）。所以不存在几台设备同时远程的情况，要做好的是换着用和换手。

不切到 Snug 的屏时，一切和原版 UU远程 一样。这条不变（主动打开「设为主屏」的除外，见 2.6）。

## 2. 产品形态

### 2.1 屏幕列表

设置里有一张屏幕列表，由用户自己增删。每一项是一块虚拟屏（下面只示意有哪些信息，界面长什么样以 UI 原型为准，见第 8 节第 2 步）：

```
屏幕
  [开]  Snug 手机屏          竖 · iPhone 17 Pro Max
  [开]  Snug · iPad Pro 11   横 · iPad Pro 11-inch (M4)
  [关]  Snug · MacBook Air   横 · MacBook Air 13 (M4)
  添加屏幕…
```

- **开关**：只有开着的屏才会在远程时建出来。大多数人只开一块，体验和现在完全一样。
- **不限制同时开几块**（11-17 主人定）：UU 一次只让一台设备控制，同一时间只用到一块屏；多开的屏留给同一台设备横竖切换、换设备接管时不用改设置。设置里在屏幕列表下面写明这一点，用不到的可以关掉，不替用户堵死多开。
- **方向**：添加时选横或竖，之后不改，想换方向就再加一块。改方向要撤屏重建，UU 也得重选屏，和换一块新屏没有区别；而且名字、可选的型号都跟着方向走。
- **型号**：从机型库里选，或者自己填分辨率。型号随时能改，改了在线换比例，不撤屏（现有能力）。
- **名字**：「显示器」设置和 UU远程 屏幕列表里显示的名字，添加时按型号生成，用户可以改。UU 列成「显示屏 N (名字)」，用户就靠它认出该选哪块（V3）。同一身份改名，系统仍当作同一块屏，记住的档位不丢（V7）。
- 远程进行中拨开关、增删屏，只影响那一块：正在看的那块屏不卡、点按照样准（V2）；关掉的正是正在看的屏时，UU 自动回到主屏，连接不断。所以拨开关时不用提示。

### 2.2 型号由用户选，程序不识别控制端

- 不读 UU 的设备列表，不替用户打开 UU 主界面，不按控制端名字猜设备类型。
- 每块屏用什么比例、有什么行为，只取决于用户的设置。同样的设置，每次结果都一样。
- 代价：同一块屏给两种设备轮流用（今天 iPad、明天笔记本）时，换设备要改一次型号。经常换着用不同设备的，各加一块屏，用哪台就在 UU 里选哪块。

### 2.3 行为跟着型号的类别标签走

机型库里每个型号都带类别标签：手机、平板、电脑。标签在搜集数据时按官方规格写定；自己填的型号由用户选类别。

| 类别 | 手势翻译 | 放上来时放大字号 | 基准尺寸（见 4.4） |
| :--- | :--- | :--- | :--- |
| 手机 | 开（设置里的手势总开关关掉就不开） | 是 | 竖屏沿用 540 点宽；横屏取 2 倍高清里最窄的一档（短边 525 点），字最大 |
| 平板 | 开（同上） | 是，默认 2 级（V10） | 比手机松一些：1 个 Mac 点约合 1.24 个平板点（V10） |
| 电脑 | 不开 | 否 | 电脑自己的逻辑分辨率，和它本机看着一样大；有刘海的扣掉顶上那一条 |

- 行为只看标签，不看屏的形状。竖着用显示器的电脑，在竖屏里自己填分辨率、类别选电脑，照样不开手势。
- 尺寸重叠不影响判断。iPhone Duo 内屏 1878×2670（高宽比 1.42）和 iPad Pro 11（M4）1668×2420（1.45）形状几乎一样，一个是手机一个是平板，靠标签区分。
- 型号列表默认按方向筛：竖屏只列手机和平板，横屏三类都列。自己填不受限制。

### 2.4 每块屏上有什么

三类屏都有 App 资源库，入口不一样：

- 手机、平板屏：和现在一样，底部有小横条，App 资源库铺在屏上。小横条是给手机、平板用的，在触屏上管 App 和窗口不方便，靠它回到资源库。横屏按宽排版（App 资源库分两栏），竖屏和现在一样，具体样式实现时出图确认。
- 电脑屏：不放小横条。电脑有鼠标、菜单栏和程序坞，用起来本来就方便；App 资源库从这块屏菜单栏上的 Snug 图标打开（11-17 主人定）。电脑屏也要 App 资源库：已经开在别的屏上的窗口不会自己过来，点程序坞里的图标只是把那个窗口在原来的屏上提到前面（V9）。
- 屏上「型号」入口改的是这一块屏的型号。
- 截图键（设置里开着时）在手机、平板屏的小横条上，截的是那块屏上放着的窗口。
- 在手机、平板上退出某块屏，只退这一块，这次远程内不再加它。
- iPad 上 UU 的圆形菜单按钮压在右上角约 45 点（V6），平板屏上 Snug 放在右上角的按钮（「型号」「退出」）要让开约 50 点。

### 2.5 升级与默认

- **老用户升级**：现在的配置迁成列表里的一项「Snug 手机屏 · 竖 · 原来选的型号」，开关沿用原来的手机屏总开关。名字和屏的身份都不变，UU 里看到的和以前一样。
- **新装**：列表里默认只有这一项。
- **电脑屏**要用户自己加。添加处说明一句：没接显示器的 Mac，加任何一块屏都会顶掉系统的默认屏（#8），这和手机屏一样。

### 2.6 设为主屏（可选）

为 #10 那样的用法准备：远程时把 Snug 的屏当成主屏，接着做主屏上的事。

- 设置里加一项「主屏」，默认「不改」。可以从屏幕列表里选一块，只能选一块。
- 选了以后，那块屏建出来就设为主屏；撤掉之前，先把原来的主屏设回去。
- 改主屏前，先把原来的主屏和各屏的排布记进还原账；Snug 崩溃后，下次启动按账还原。
- 只改主屏，不关物理屏。默认关着，不选的人完全不受影响。
- 实测（V11）：
  - 设成主屏后，UU 新连上来两路推流都在这块屏上，不用手动选屏；菜单栏、程序坞也到了这块屏上。
  - 原主屏上的窗口全部跟着主屏搬到这块屏上，别的屏上的窗口不动。用户连上就是自己原来的桌面，不用靠 App 资源库一个个拉。
  - 撤屏前设回原主屏，这些窗口自己回到原主屏（位置偏约 20 点）。
  - 物理屏仍在，UU 里照样能切过去。
  - 远程中途改主屏，UU 正在推的那一路不跟着跳。
- 由此有一个代价：第一次连接时，屏是连上之后才建的，建好设主屏时 UU 正推着原主屏、不会跳过去，原主屏上的窗口却搬走了，用户看到的是一块空屏，要在 UU 里选一次屏。同一次远程里断开重连、换手接管时，屏还在、已经是主屏，就直接落在这块屏上。这个代价接受（2.8）。

### 2.7 不做

- 关物理屏
- 一块屏在横竖之间切换
- 自动识别控制端的设备类型、型号或分辨率
- 几台设备同时远程时按设备分别撤屏（UU 一次只让一台控制，见第 1 节）

### 2.8 实测后定下的三项

1. ~~电脑屏的小横条~~：已定（11-17），电脑屏不放小横条，App 资源库从菜单栏的 Snug 图标打开，见 2.4。程序坞会搬到电脑屏的底边（V9），不放小横条也就不冲突。
2. ~~设主屏时的第一次连接~~：已定（11-17），接受。第一次连上在 UU 里选一次屏，和现在用手机屏一样；同一次远程里重连、换手都直接落在这块屏。不做「设主屏时屏常驻、不等远程」：坐在这台 Mac 前的人会找不到菜单栏和程序坞。
3. ~~竖屏手机的基准宽度~~：已定（11-17），不动，沿用 540。降到 525 字只大约 3%，老用户升级后无感更要紧。

2.8 的三项都已定。

## 3. 生命周期

分两层看：屏在不在，屏上的东西。

### 3.1 屏在不在

由策略层的一个纯函数 `ScreenPlan` 决定（见 4.2），屏幕模块本身不带规则。

- 远程开始时，建出所有开着的屏。
- 远程结束（推流全停，过了 15 秒重连等待期）时，全部撤掉。
- 远程中途不按设备增减屏，只跟着用户拨开关、增删屏。
- 换手：一台连着时另一台点「接管设备」，前一台的推流停掉后 0.6～0.7 秒新的一台就起推流（V12），远在重连等待期之内，算同一次远程，屏不撤不建。
- 撤掉的正是正在看的屏时，UU 0.9 秒后自动改推主屏，连接不断。

**屏必须在设备选中它之前就在。** UU 每次新连接都从主屏开始推流，用户要在 UU 的屏幕列表里手动选屏。所以有人连进来时，就要把开着的屏都建好，不能等谁选了再建。

### 3.2 屏上的东西

每块屏完全独立。放着哪个窗口、在哪一档、字号放大几级、App 资源库露没露、有没有正在打开的 App、有什么提示，都是这块屏自己的。在一块屏上做事、切去别的屏、断网重连，不碰别的屏上的任何东西。

一个窗口同一时刻只在一块屏上：
- 在 B 屏上点了已经放在 A 屏上的窗口，就把它挪到 B 屏，A 屏回到 App 资源库。
- 原位记录跟着窗口走，中间不还原一次。
- 字号按 B 屏的类别调，挪到电脑屏上就缩回原样。

### 3.3 拓扑变化

加或撤任何一块屏，macOS 都会挪窗口、重排各屏的位置（V2 里正在看的屏被挪了 264 点），还会把别的屏拨回它给这组屏幕记的模式。UU 正在推的那一路不受影响：不停、不重开，点按照样准（V2）。因此：

- 屏的增删一次一步、排队做。同一批增删，前后只记一次周围的样子、只善后一次（见 4.2 的 ScreenSet）。
- **撤屏前清场**：屏上所有窗口都要先挪走，不只是 Snug 放上去的那一个。Snug 放上去的按账放回原位；其余的（用户在这块屏上直接开的、设主屏时跟过来的）挪到主屏上，大小不超过主屏。实测撤屏后，留在上面的窗口停在所有屏的范围之外，系统不挪回来（第 7 节）。
- 现有的保护全部保留，改成每块屏各自执行：
  - 最短存活 2.5 秒
  - 建了不上线就换备用身份
  - 加屏失败按 5 / 15 / 30 秒重试
  - 撤了没下线，等它真下线再善后
  - 远程中撤屏，只设回本次登录
- 设为主屏（2.6）也是一次拓扑变化：建好那块屏之后设主屏；撤之前先设回原来的主屏（跟过去的窗口随之回到原主屏），再清场、再撤。同样排在队里。

## 4. 架构

### 4.1 总图

箭头是依赖和调用的方向，只朝一个方向，没有环。

```
Snug（App 层）
│
├─ AppController ··········· 装配层：唯一写配置、唯一把模块接起来的地方
│    │
│    ├──▶ ScreenPlan ········· 策略（纯函数）：配置 + 会话 → 此刻要哪些屏、每块的比例和行为
│    │
│    ├──▶ DeskSet ············ 多块屏的总管：一条队、还原账、字号簿、留下的账、App 级的动作
│    │      ├──▶ Desk × N ···· 一块屏上的事：放窗口、App 资源库、选档、字号
│    │      │      └──▶ ScreenSet（只读查询 + 换档）
│    │      └──▶ ScreenSet ···· 屏幕模块（单一数据源）：建、撤、换比例、换档、善后
│    │
│    ├──▶ TouchTap ··········· 手势：只认一组矩形，矩形里的触摸按 iPhone 手势翻译
│    │
│    └──▶ ScreenWindows × N ·· 手机、平板屏上的面板（App 资源库、小横条），只读 Desk 的状态
│                               （电脑屏的 App 资源库从菜单栏的 Snug 图标打开）
│
├─ 设置页 ··················· 屏幕列表；改动经 AppController 写进配置
│
SnugCore（纯逻辑；系统能力全部经协议注入，可以用假的测试）
│    ScreenPlan · DeskSet · Desk · ScreenSet · ScreenFit · DeviceCatalog · RemoteSession
│         │
│         ▼ 只依赖协议
│    VirtualDisplays · WindowControl · AppControl · Timeline
│         ▲
│         │ 实现
SnugSystem
     VirtualDisplayService（CGVirtualDisplay）· DisplayArrangement（设主屏、还原排布）
     · WindowService · AppService · TouchTap
```

谁知道什么。依赖拆得干不干净，看这张表：

| 模块 | 知道手机/平板/电脑 | 知道横/竖 | 直接动虚拟屏 |
| :--- | :--- | :--- | :--- |
| ScreenPlan | 是，只读型号的类别标签 | 是，只读配置 | 否 |
| ScreenSet | 否 | 否，只认宽 × 高和身份 | 是（经 VirtualDisplays） |
| DeskSet / Desk | 否，只认 ScreenPlan 给的行为参数 | 否 | 否，换档经 ScreenSet |
| TouchTap | 否 | 否 | 否 |
| ScreenWindows | 否 | 只按宽高比排版 | 否 |

「手机和平板要手势、电脑不要」这条规则只在 ScreenPlan 里出现一次。加一种设备（比如安卓平板）只改机型库的数据；要让某类设备的行为不一样，只改 ScreenPlan。

### 4.2 模块

#### ScreenPlan（新增，SnugCore，纯函数）

```swift
/// 一块屏此刻该在，以及它该是什么样
public struct ScreenWish: Equatable, Sendable {
    public let id: ScreenID           // 配置里那一项的 id
    public let spec: ScreenSpec       // 身份：名字、序列号、像素上限、物理尺寸
    public let fit: ScreenFit         // 比例和档位
    public let behavior: ScreenBehavior
}

public struct ScreenBehavior: Equatable, Sendable {
    public var gestures: Bool         // 这块屏上翻不翻译手势
    public var zoomSteps: Int?        // 放上来时默认放大几级；nil 表示不调字号
}

public enum ScreenPlan {
    public static func wishes(config: AppConfig, remote: RemoteFacts, dismissed: Set<ScreenID>,
                              trusted: Bool, preview: Bool) -> [ScreenWish]
}
```

- 输入只有这几样：配置；会话给出的事实（在不在远程、含重连等待期；画面那一路在推哪块屏）；在手机上退出过的屏；辅助功能权限；预览模式。
- 替代现在的 `AppController.wantsPhoneScreen` 和 `RemoteSession.wantsPhoneScreen`。
- 3.1 的规则只写在这里，换规则不动任何模块。
- 每拍算一次，交给 DeskSet；结果没变就什么都不做。

#### ScreenSet（新增，SnugCore，从 PhoneDesk 的「加屏、撤屏」拆出）

屏幕模块，单一数据源。此刻有哪几块 Snug 屏、各是什么状态、什么比例、在哪一档，只有它知道，也只有它能改。

对外接口：
- `apply(_ wishes: [ScreenWish])`：对照现状做差量。新的建出来，没了的撤掉，比例变了的在线换（同一身份），其余不碰。
- 查询：`display(for:)`、`width`、`windowArea`、`bounds`、`fit`。
- `setWidth(_:_:)`：换档，Desk 选好档后调用。
- 状态：`[ScreenID: ScreenState]`，取值为 off、preparing、ready(DisplayID)、failed。

从 PhoneDesk 搬来、逻辑不变、改成按块执行的：`reconcile`、`addScreen`、`retireDisplay`、`scheduleRetry` / `cancelRetry`、`Surroundings`、`settle`、`Retiring`、`persistOwed`、`settleDisplays`，以及最短存活。

规则：
- 一批差量里有多块屏要建或撤时，先记一次周围的样子，再逐块建撤（每块之间照样等系统稳定），最后善后一次。
- 善后放回窗口时，跳过所有放在 Snug 屏上的窗口。这组窗口由 DeskSet 注入一个闭包来取，ScreenSet 不认识 Desk。
- 主屏：`ScreenWish` 里标着哪块要设为主屏（最多一块）。建好后设为主屏；撤之前先设回原来的主屏，再由 DeskSet 清场。改之前把原主屏和排布记进还原账，启动时有没销的账就按它还原。
- 依赖：VirtualDisplays、WindowControl（只用 `snapshot` / `restore`）、Timeline；设主屏和还原排布经 `DisplayArrangement`（SnugSystem 里已有，实验屏工具在用，要抽成协议注入）。

#### Desk（由 PhoneDesk 瘦身改名，SnugCore）

一块屏上的事，每块屏一个：

- 状态：放着的窗口、App 资源库露没露、正在做的事、提示、关闭按钮的位置、在手机上退出过没有。
- 动作：放窗口、放回、回到列表、回到窗口、调字号；选档（`wantedWidth`、`fill`、`reveal`、`refill`、`recheck`）。
- 行为参数来自 `ScreenBehavior`，例如电脑屏不调字号。
- 不建屏、不撤屏；换档经 ScreenSet。

#### DeskSet（新增，SnugCore）

多块屏的总管。所有动作排成一条队（现有的 `SerialLane`），屏的增删和窗口的挪动不会交错。

- `setWishes`：先给要撤的那几块屏清场（3.3）：它们的 Desk 按账放回放上去的窗口，再把屏上剩下的窗口挪到主屏；然后交给 ScreenSet 做差量，最后给新屏建 Desk。设了主屏的，ScreenSet 先设回原主屏，再清场。
- 带屏号的意图（「在 B 屏上放这个窗口」）转给对应的 Desk。窗口在别的屏上时，先从那块屏转过来（见 3.2）。
- App 级的动作放在这里：打开、新建窗口、退出 App、强制退出、关窗口。
  - 退出 App 前，把它在所有屏上的窗口都放回原位。
  - 「正在退出」「正在关闭」是全局状态，每块屏的 App 资源库都显示。
- 共用的账：
  - 还原账，改成每块屏一份，见 5.5
  - 字号簿 `ZoomBook`
  - 留下的账 `LeftBehindBook`
  - 启动时按账还原（`recover`），等窗口回来再还（`checkReturns`）

#### RemoteSession / CaptureSessionState（小改）

同一时刻只有一台控制端，推流的规律已经测清（第 7 节）：每次连接两路，画面一路、主屏常驻一路；切屏只换画面那一路；断开时两路一起停；接管时前一台的两路停掉，0.6～0.7 秒后新的一台起两路。

- 现有的判断照旧：有没有活着的推流、编码会话中途续推、3 秒宽限、15 秒重连等待期。换手落在重连等待期之内。
- 对外给出 `RemoteFacts`：在不在远程（含重连等待期）、画面那一路在推哪块屏。
- 删掉只为几台同时连着写的处理（见 5.2）。

#### TouchTap（改）

- `setRegion(TouchRegion?)` 改成 `setRegions([TouchRegion])`。
- 按下的那一刻落在哪个矩形里，这一下就按那个矩形的缩放来翻译；不在任何矩形里的原样放行。
- 手势逻辑 `TouchTranslator` 不变。

#### ScreenWindows（由 PhoneScreenWindows 改，Snug）

每块就绪的手机、平板屏一组面板，跟着那块屏的 Desk 状态走。横屏时 App 资源库横排。电脑屏没有面板，它的 App 资源库从菜单栏打开（2.4）。

#### 屏的身份

系统按身份（vendorID + productID + 序列号）记住一块屏的设置、排布和 ICC 文件，所以每块屏一组自己的身份：

- vendorID 沿用 `'SN'`，用来认出自己建的屏。productID：竖屏沿用 `0x00F0`，横屏用 `0x00F1`。
- 序列号在添加时从没用过的号段里分配，写进配置。号码永不复用，删掉的屏的号也不回收，免得系统把旧屏的记忆套到新屏上。迁移来的那块竖屏沿用现在的 `200_000_108 / 118 / 128`。
- 像素上限按方向各定一个：竖屏 2160×4320 不变，横屏 6144×3840（V5：新身份当场上线，框得住 6K 的 3008×1692 的 2 倍）。像素上限必须和屏的方向一致，横屏上限的屏上，竖着的档不能用（V4）。
- 物理尺寸按像素上限、约 220ppi 折算，和现在一样。按真实像素密度折算的话，全新身份的屏不会上线。
- 同时最多 4 块屏（V8：四块同时在没问题，现实用不到更多）。

### 4.4 每块屏的尺寸（推广 ScreenFit）

现在的 ScreenFit 只服务竖屏手机，改成按方向、型号和类别来算：

- **比例**：把型号的屏幕按这块屏的方向摆好，扣掉 UU 在这个方向上压住画面的部分。竖屏手机现在是上下各扣 91 点。手机横屏扣的是左右：UU 的工具栏在右边压约 82 个手机点，左边（灵动岛那侧）压一条约 72 点的暗带，上下不压（V6，精确数等量完截图定；11-17 主人定扣左右）。平板不扣，横竖都铺满（V6）。电脑：UU 全屏时只是等比缩小、四周留黑边，不挡东西（V6，MacBook Air 有刘海，顶上空 33 点、左右各 25 点，画面缩小约 3.5%）。有刘海的 MacBook 扣掉顶上这一条，画面正好一像素对一像素、没有黑边（Air 13 M4：1470×956 → 1470×923）；没刘海的电脑铺满。UU 窗口模式跟着窗口缩放，不管（11-17 主人定）。
- **2 倍高清门槛**（所有屏都要满足）：按屏自己的方向算，竖横同一条，长边 ≥ 800、短边 ≥ 525 点（V4）。
- **基准宽度**（11-17 逐项定）：
  - 手机竖屏：沿用 540 点宽，不降到 525（2.8）。
  - 手机横屏：门槛里最窄的一档，短边 525 点，字最大；扣完左右约 940×525 点，精确数等量完截图定。
  - 平板：不用最窄一档。按 V10 的体感，1 个 Mac 点约合 1.24 个平板点，即平板的逻辑分辨率除以 1.24。iPad（第 10 代）竖 660×950、横 950×660 点；最窄一档（556×800）字还要大约 20%，偏大。
  - 电脑：电脑自己的逻辑分辨率，和它本机看着一样大；有刘海的扣掉顶上那一条（见上面「比例」）。
- **档位**：从基准宽度往上，宽高比都相同，最宽不到基准的 3 倍；App 限定了最小尺寸时，照现在的办法换档。同一块屏上登记相差太大的档，小的那档会不能用（V4：和 3008×1692 登记在一起时，1141×525 不能用）。
- **比例范围**按方向分：竖屏 1～2（不变）；横屏实测过高宽比 0.46（手机横）、0.65（MacBook Air）、0.695（iPad）都能用，上下限按机型库里的极值定。
- **面板和手势阈值的缩放**：现在按 540 点宽设计，只对竖屏手机成立。改成按「这块屏上的一个点在控制端上实际有多大」换算，用型号的逻辑分辨率来算。V10 在 iPad 上的数据点：660 点宽、面板和手势阈值不缩放（1 个 Mac 点约合 1.24 个 iPad 点），用着都顺。横拿手机还没用过。
- ScreenFit 由 ScreenPlan 按配置算好，放进 ScreenWish；ScreenSet 和 Desk 只用不算。

## 6. 为什么这样设计是合理的

1. **顺着 UU 的硬约束走。** UU 每次新连接都从主屏开始，用户反正要在 UU 里选一次屏；UU 只在选屏那一刻按屏幕尺寸开推流，屏中途改比例，画面就会错位。所以每块屏固定方向、由用户自己选，不需要任何横竖切换逻辑，也就没有「换了方向要重选」的代价。
2. **单一数据源。** 只有 ScreenSet 碰虚拟屏，屏的增删排队、一次一步、前后善后。WindowServer 在拓扑变化上很脆弱：屏建好太快就释放会卡死，热插拔还没处理完又建屏会崩。把所有拓扑变化收在一处，现有的保护才能覆盖到每一块屏。
3. **差异是数据，不是代码。** 手机、平板、电脑、横、竖，在屏幕模块看来都只是宽 × 高。加一种设备只改机型库；没有子类，也就不会出现「某类设备的代码路径没测到」。
4. **行为看写明的标签，不靠猜。** 设备类别是型号上写明的标签，不从形状或名字推断。形状重叠、控制端改名、竖着用的显示器，都不会认错。
5. **结果可预期。** 决定建哪些屏、各有什么行为的输入，只有用户的设置和远程在不在。UU 一次只让一台设备控制，屏在不在只看远程在不在，换手不撤不建。不读 UU 的界面来做决定，同样的设置每次结果都一样，问题能复现、能测。
6. **规则集中在一个纯函数里。** 生命周期规则、类别到行为的映射，都在 ScreenPlan 里。以后要换规则（比如某类设备的行为），只改这一处，有单测兜着，其他模块都不动。
7. **按块隔离。** 每块屏一个 Desk，一块屏出了问题（建不出来、窗口卡住），不连累别的屏。窗口的挪动和 App 级的动作仍在同一条队里，不会两块屏抢着挪同一个窗口。
8. **大多数人无感。** 只开一块屏的人，行为和现在一模一样；配置自动迁移，屏的名字和身份不变。设为主屏默认关着，要用的人自己选。
9. **依赖单向。** SnugCore → SnugSystem → Snug 的分层不变；SnugCore 里 ScreenPlan、DeskSet、Desk、ScreenSet 之间也只朝一个方向，全部能用假的系统能力测试。

### 只用 Mac 的实测发现（11-17，`--probe-screens`）

结论如下，已据此修订第 4 节。

- **2 倍门槛按屏自己的方向算**：屏按自己的方向（像素上限的横竖）看，长边 ≥ 800 点、短边 ≥ 525 点，2 倍模式才能当桌面用。
  - 横屏：800×525 行；800×524、799×540、1200×520 不行。
  - 竖屏：525×800 行；524×800、540×799 不行。以前记的「宽 ≥ 540」是因为没试过更窄的，真正的门槛是 525。
  - 像素上限 4000×2000、6000×2000、4000×3000、6144×3456 结果一样，和上限大小无关。
  - 横屏上限的屏上，竖着的 540×800 不能用。所以每块屏的像素上限必须和它的方向一致。
- **同一块屏上不要登记相差太大的档**：和 3008×1692 登记在一起时，1141×525 不能用；单独登记、或和同比例的档（到 3000 宽）登记在一起都能用。按现在的做法，一块屏只登记同一比例、从基准宽度往上不到 3 倍的档，实测都能用：
  - 手机横屏 1141～3000 宽（比例 0.46）
  - iPad 800～1600 宽（0.695）
  - MacBook Air 1470～2940 宽（0.650）
- **对几个尺寸的直接影响**（扣 UU 工具栏之前的数，V6 后再修）：
  - 手机横屏：短边到 525 就行。17 Pro Max 横放约 1141×525 点，字比 iOS 自己横屏时略小，不必宽到 1700 多点。
  - iPad（第 10 代）横屏：最窄的 2 倍档是 800×556 点，比 iPad 自己的 1180×820 点还大。平板要不要用最窄一档，按 V10 定（已定：不用，见 4.4）。#7 原型的 1150×803 是照「高 ≥ 800」凑的，不是门槛。
  - 竖屏手机：基准宽度可以从 540 降到 525，字再大 3%（2.8 已定：不降）。
- **身份**：新身份上线快，一个身份一份 ICC；改名不算新屏。屏名可以跟着型号走，也可以让用户改。
- **数量**：四块同时在没问题，上限定 4。

### 第一轮实测发现（11-17，手机 + MacBook Air）

截图在 `~/Downloads/IMG_1298.PNG`（竖屏）、`~/Downloads/IMG_1299 2.PNG`（横屏）。手机是 iPhone 17 Pro Max。

- **V6 手机竖屏**：540×950 整块都看得见，落在顶部黑边和底部工具栏之间，和现在的设计一致。
- **V6 手机横屏，要改比例算法**：1141×525 是按整块手机屏的比例（2.173）算的，画面铺满了整块屏，没有黑边。但 UU 横屏时把工具栏放在**右边**，压在画面上，约 82 个手机点；左边（摄像头那侧）也压一条半透明的暗带，约 72 个手机点；上下没被压。所以横屏要扣的是左右两边，不是上下。粗估扣完后手机横屏约 940×525 点，字比 1141 宽时更大。精确数等截图量完再定。
- **V1 只有一台设备时的推流规律**：
  - 每次连接起两路推流，前后差约 0.4 秒：第一路是画面，第二路常驻在主屏。
  - 切屏：画面那一路停掉，约 40 毫秒后在新屏上起一路新的。
  - 断开：两路在 2 毫秒内一起停。
  - 推流的地址会复用：停掉的地址后面会再分给新的推流，所以只在「同时活着的几路」之间唯一。
  - 06:31:55 有一次断开后 0.6 秒又连上，直接接着推横屏，没有回主屏。这和「新连接一律从主屏开始」不一样，猜是 UU 自己的快速重连，未验证。
- **同一时刻只能一台设备控制（改变范围）**：Air 连着时，手机去连这台 Mac，无论怎么试都只弹「当前设备正在被控中，接管设备后可进行远控」，点了接管就把 Air 挤下去。UU 官方终端教程也写着「使用过程中若被其他设备接管，当前会话会自动断开」。所以「几台设备同时远程、一台走了别的屏要留着」的情况不存在，要做好的是换手（V12）。#3 的日志里列表上同时有两台，但没法确认当时是同时在用还是表格没刷新，不作数。已据此改第 1～6、8 节，「同时」「逐块撤」都删了。
- **V9 电脑屏当桌面**（MacBook Air 连「显示屏 5 (Snug 测试 MacBook)」，UU 按「显示屏 N (屏名)」列出，和手机上一致）：
  - 程序坞：鼠标碰这块屏底边，程序坞搬过来；这台 Mac 没开自动隐藏，搬过来后一直显示。电脑屏因此不放小横条（2.4、2.8 已定）。
  - 新开的 App（备忘录）落在这块屏上；屏顶有菜单栏，左边显示的是备忘录的菜单。
  - 已经开在内建屏上的窗口不会过来：点程序坞的访达，只是把内建屏上原有的访达窗口提到前面，在 UU 里看不到。和手机屏一样要靠 App 资源库拉过来，2.4 的设计成立。
- **撤掉正在看的屏**：Air 看着 MacBook 测试屏时把它撤掉，UU 那一路推流因为屏没了停掉，0.9 秒后自动改推主屏，不断开，Air 上只是回到了内建屏。远程中关掉正在用的那块屏不会把连接弄断。
- **V11 设主屏，窗口跟着主屏走**：设成主屏后，原主屏上的窗口全部搬到新主屏，撤屏还原后又全部回来；别的屏上的窗口跟着自己的屏挪。设主屏打开时，用户一连上就是自己原来的桌面，比预想的好。

## 8. 实施顺序

每一步都先写测试、看它失败，再实现；一步验完再走下一步。全部在 `multi-screen` 分支上做。

1. **实测与评审**（做完）：
   - 加 `--probe-screens`，两轮实测（手机 + MacBook Air、iPad）测完 V1～V12，按结果修订了第 1～6 节，2.8 三项和各设备的扣边、平板大小都已定（11-17）。
   - 还剩手机横屏的两件小事：量准左右扣多少；看横拿时 UU 右边的工具栏会不会自己缩回。做第 5 步「横屏和平板」前补上。
2. **UI 重组：原型和设计规范**（做完，11-17 主人确认）：
   - 原因：功能越加越多，原来的界面几乎都是从上往下一项项排下来，内容不分层；多屏又要加屏幕列表、每块屏的型号和开关、设为主屏、电脑屏的菜单栏入口。
   - 顺序是先定令牌、再画原型（主人定，不能反）。令牌在 `design/design-tokens.json`，分 `mac`（Mac 上的界面）和 `touch`（手机、平板屏上的面板）两套；带 `system` 的颜色在 Swift 里用系统语义色，`light` / `dark` 只给原型预览。原型在 `design/prototype/index.html`，数值全部取令牌生成的 CSS 变量。
   - 定下来的界面（以原型为准）：
     - **菜单栏菜单**：顶上一行状态（远程中 · 设备 · 正在看哪块屏）；「App 资源库」（给电脑屏，在哪块屏的菜单栏点就在哪块屏打开）；设置…、关于 Snug、退出 Snug。
     - **设置窗口分三页**（顶部分页，macOS 设置窗口的样式）：
       - 屏幕：远程状态；屏幕列表（类别图标、名字、横竖·型号、「在看」标记、开关、ⓘ 进详情）；列表下一行结论「同一时间只用到一块屏，用不到的可以关掉。」，行末「为什么？」点开气泡讲两个理由（横竖切换、换设备）；「添加屏幕…」；设为主屏（默认「不改」）。
